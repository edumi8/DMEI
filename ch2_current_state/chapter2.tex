\chapter{Current State of the Target Environment}
\label{chap:current_state}

This chapter characterizes the current operational state of the target \ac{CICD} environment before intervention. The objective is to document the baseline architecture currently mounted in production-like operation, motivate the proposed observability solution, and support later comparison during implementation and evaluation.

\section{Infrastructure and Platform Baseline}

The target environment is an on-premise, containerized \ac{CICD} platform distributed across mixed operating systems (Linux and Windows). Core platform services include source control, pipeline orchestration, static analysis, software composition analysis, and artifact management. The environment is operationally relevant because failures in one service can propagate across the full delivery pipeline.

\subsection{Baseline Node and Service Topology}

The baseline architecture is represented as a structural node-to-service topology diagram. This view intentionally focuses on host and service placement (without runtime interaction links). The diagram source is maintained in Mermaid format to simplify iterative updates during thesis development: \texttt{ch2\_current\_state/assets/baseline-architecture.mmd}.

At infrastructure level, the mounted structure is centered on four hosts: \texttt{le-s-po-lin1}, \texttt{le-s-po-lin2}, \texttt{le-s-po-app1}, and \texttt{le-s-po-win1}. The primary host (\texttt{le-s-po-lin1}) provides shared \ac{CICD} control services. The remaining nodes provide execution capacity and environment support: a secondary Linux host with database and test support (\texttt{le-s-po-lin2}), an application-side deployment host for test and staging workloads (\texttt{le-s-po-app1}), and a Windows worker for platform-specific execution tasks (\texttt{le-s-po-win1}).

\section{Current Observability Posture}

The current monitoring posture is predominantly reactive. Diagnostic activities rely on manual inspection of container logs, ad-hoc resource checks, and service-specific troubleshooting interfaces. Telemetry remains fragmented across tools, with limited cross-service correlation and no consolidated operational view.

In practice, the primary diagnostic mechanism is \texttt{docker logs}. Teams typically inspect container output only after incidents occur, which limits early detection and increases mean time to identify root causes. This log-only approach also provides weak correlation with host-level resource behavior, inter-service dependencies, and end-to-end request execution.

\section{Operational Pain Points}

The baseline assessment highlights recurrent constraints:
\begin{itemize}
    \item Delayed incident detection due to limited proactive alerting.
    \item High diagnostic effort caused by fragmented logs and metrics.
    \item Limited historical evidence for capacity planning and trend analysis.
    \item Inconsistent troubleshooting procedures across Linux and Windows hosts.
\end{itemize}

These pain points establish the need for a structured observability architecture that integrates metrics, logs, and traces under the real constraints of the environment.
