ABSTRACT
Microservices have emerged as a popular pattern for developing large-scale applications
in cloud environments for their ﬂexibility, scalability, and agility beneﬁts. However, microser-
vices make management more complex due to their scale, multiple languages, and distributed
nature. Orchestration and automation tools like Kubernetes help deploy microservices run-
ning simultaneously, but it can be diﬃcult for an operator to understand their behaviors,
interdependencies, and interactions. In such a complex and dynamic environment, perfor-
mance problems (e.g., slow application responses and high resource usage) require signiﬁcant
human eﬀort spent on diagnosis and recovery. Moreover, manual diagnosis of cloud mi-
croservices tends to be tedious, time-consuming, and impractical. Eﬀective and automated
performance analysis and anomaly detection require an observable system, which means an
application’s internal state can be inferred by observing and tracking metrics, traces, and
logs. Traditional APM uses libraries and SDKs to improve application monitoring and trac-
ing but has additional overheads of rewriting, recompiling, and redeploying the applications’
code base. Therefore, there is a critical need for a standardized automated microservices
observability solution that does not require rewriting or redeploying the application to keep
up with the agility of microservices.
This thesis studies observability for microservices and implements an automated Ex-
tended Berkeley Packet Filter (eBPF) based observability solution. eBPF is a Linux feature
that allows us to write extensions to the Linux kernel for security and observability use
cases. eBPF does not require modifying the application layer and instrumenting the indi-
vidual microservices. Instead, it instruments the kernel-level API calls, which are common
across all hosts in the cluster. eBPF programs provide observability information from the
lowest-level system calls and can export data without additional performance overhead. The
Prometheus time-series database is leveraged to store all the captured metrics and traces for
analysis. With the help of our tool, a DevOps engineer can easily identify abnormal behav-
ior of microservices and enforce appropriate countermeasures. Using Chaos Mesh, we inject
anomalies at the network and host layer, which we can identify with root cause identiﬁcation

using the proposed solution. The Chameleon cloud testbed is used to deploy our solution
and test its capabilities and limitations.

1. INTRODUCTION
Microservices are an architectural and organizational approach to software development
where software is composed of small independent services that communicate over well-deﬁned
APIs. Most of the recent client-server web applications are adopting microservice architec-
tures due to their beneﬁts like modularity and scalability [
 1
 ] over their monolith counter-
parts [ 2 ]. The highly networked microservice architecture brings in challenges of observability
into the underlying functioning of the application, introduces networking overheads [
 3
 ], and
inﬂuences the architectural design of our applications [
 4
 ]. To manage the growing complex-
ity of microservices the concept of microservice mesh Linkerd [
 5
 ] was introduced to abstract
the service-to-service communication away from the application pod to a “sidecar” proxy. A
service mesh abstracts networking logic into a parallel layer of infrastructure i.e. the data
plane and the control plane. The control plane is responsible for conﬁguring the network
policies and routing paths inside our mesh whereas the data plane sidecar is responsible for
using lightweight communication protocols like REST or RPC to communicate between the
various microservices using the speciﬁed routes. Although the control plane can conﬁgure the
microservices, conﬁguration drift [
 6
 ] is common in cloud environments which occurs when
the actual known state of the infrastructure diﬀers from the prior conﬁguration. Therefore,
there is a critical need for real-time observability in our service mesh to be able to identify
performance issues and analyze the causes of latency.
The deﬁnition of observability for a software system is its “capability to allow a human to
ask and answer questions” [ 7 ]. The more questions we can ask and answer about the system,
the more observable it is. The open-source community deﬁnes observability with it’s three
pillars i.e., metrics, logs and traces [
 8 ].
• Metrics: Metrics are numerical measurements that are obtained by observing a system
from the outside. They represent data that is measured over speciﬁc intervals of time,
and their power lies in the ability to use mathematical modeling and prediction to gain
insight into the behavior of a system in the present and future. Due to their numeric
nature, metrics can be easily stored, processed, compressed, and retrieved, making
14



--- PAGE 15 ---
them ideal for extended data retention and quick querying. As a result, metrics are
well-suited for creating dashboards that illustrate historical trends.
• Logs: The sequence of events generated inside a singular application. Logs are records
of discrete events that have occurred over time, and they are immutable and times-
tamped. They are particularly useful in revealing emergent and unpredictable behav-
iors that may be exhibited by components of a distributed system.
• Traces: The interaction amongst multiple microservices and the ability to obtain
a macro view of the request-response lifecycle.Understanding the path of a request
enables us to identify the various services involved in its execution, while analyzing
the structure of the request provides a means to comprehend the impact of asynchrony
at diﬀerent stages of its execution.

 9
 ]
In this work, we implement a service mesh observability and tracing framework to take
application, network, host and kernel activity of containerised pods into consideration. In
the following sections we present objective and problem statement of this work is described
in detail.

1.1
Objective
The main objective of this work is to propose an observability solution framework for
Kubernetes, implement, and evaluate the use cases. The goal of the framework is to collect
metrics, logs and traces from every layer of our virtualized environment. This should allow
DevOps engineers to identify bottlenecks in microservice applications and take countermea-
sures to ﬁx them. The framework must be able to analyze all application-layer, network-layer
and kernel-layer observability data generated. The framework should not add additional la-
tency to the applications themselves and data must be measured accurately. Finally, the
solution should require minimal rewriting of application codebase of the pods and plug-in to
any Kubernetes deployment.
1.2
Motivation
With the growth of microservice development patterns in the cloud, it is becoming chal-
lenging to uniformly observe and monitor all the applications in a standardized format.
The traditional approach of using language-speciﬁc libraries and software development kits
(SDKs) requires rewriting logging functionality for each programming language microservice
we deploy, sometimes including vendor lock-ins. Additionally, the shift to public cloud service
providers (AWS, Azure, GCP) has reduced the ability of tenants to monitor the performance
or behavior of their applications. In the on-premise server model, the operator can physically
and virtually access its hardware to get in-depth, real-time information. This thesis aims to
develop a Linux observability solution that allows us to get standardized metrics, logs, and
traces directly from any application deployed in any public cloud provider as a containerized
service without instrumentation. Our solution is compatible with any Linux kernel version
greater than 3.18 and does not require rewriting or redeploying any application-layer code.
1.3
Problem Statement
The application-layer observability approach cannot keep up with the agility of the mi-
croservice software development approach since they require integrating additional code
16



--- PAGE 17 ---
within every application individually. These solutions cannot measure kernel-level perfor-
mance metrics, such as CPU time, process waiting time, I/O time, and unauthorized system
calls. Moreover, these libraries cannot fully take advantage of high-level virtualization, i.e.,
containers, and increase the memory and CPU footprint of the container images. Using
eBPF, an in-kernel virtual execution engine, we explore the possibility of achieving in-depth
observability for our microservices without modifying the application codebase.
It is important to note that companies like New Relic, AppDynamic, Sysdig, DynaTrace
and GroundCover provide similar out-of-box solutions to monitor Kubernetes clusters using
eBPF observability. However, all of them are either commercial solutions (New Relic, App
Dynamic, DynaTrace), require the use of their Kubernetes networking CNI and other cus-
tom resources (Sysdig) or store cluster metadata information in their private cloud(Ground-
Cover).
1.4
Signiﬁcance of the Proposed Work
Large collections of small servers are a particularly cost-eﬃcient platform for distributed
services workloads [
 10
 ]. With the widespread adoption of cloud computing for businesses,
the microservice pattern has emerged as the de facto standard for application development.
A clear majority (61%) of 1500 respondents to a study conducted [
 11
 ] say their organizations
have used microservices for between 1 and 5 years. In addition, 92% of organizations report
experiencing success with microservices. Although promising, the same study also high-
lighted that 60% of respondents felt their organization lacked monitoring tools, and 40% of
respondents felt the same regarding observability tools. During an interview we conducted
on September 11, 2022, Curtis Rissi, Principal Architect, AWS, stated that there is a huge
gap in the industry for cloud-native monitoring and tracing tools, especially for distributed
and containerized applications.
Containers have revolutionized the management and utilization of cloud resources. Rather
than providing each app an independent operating system like VMs, containers use names-
paces to achieve isolation in a multi-tenant cloud environment. The beneﬁt of this approach
is the less main memory footprint and ease of sharing resources. The drawback of containers
17

is their ephemeral nature; they can be spun up and terminated immediately. This makes

2. BACKGROUND AND RELATED WORK
This chapter deﬁnes the relevant background information for microservices, service mesh,
and observability.

2.1
Virtualization
Virtualization is a technology that enables the operation of multiple virtual instances of
an operating system on a single physical machine. It provides the ability to create isolated
virtual environments where various applications and services can operate independently from
each other without any interference on each other’s resources. The importance of virtual-
ization has risen signiﬁcantly in the current era of cloud computing where it is essential
to maximize the utilization of hardware resources to achieve cost-eﬀective scalability and
agility. Virtualization in cloud has led to major optimizations in networking and comput-
ing in the form of network function virtualization (NFV) and software deﬁned networking
(SDN) [
 16
 ].
With more recent advancements in containerization and coordination tech-
nologies, many companies such as Netﬂix, Twitter, and Uber [
 17
 ] are shifting away from
monolithic architectures. The shift to microservices was largely due to their ease of man-
agement and development for large, highly-distributed, replicated applications. Monolithic
architectures have several issues since their larger codebase is more diﬃcult to debug, and we
cannot independently change components without a cascading eﬀect. Other issues include
slower deployment times, diﬃculty scaling, dependency management, and tight coupling of
components.
2.1.1
Containers
Containers have emerged as a more lightweight option compared to virtual machines
(VM) due to their improved support for microservice architecture. As a result, the container
market has grown signiﬁcantly over the years, with its value projected to reach $4.6 billion
22



--- PAGE 23 ---
by 2022 from $762 million in 2016. [
 18
 ]. They are the standardized method for microservices
deployment, playing an vital role in ﬁelds such as service meshes, high-performance comput-
ing (HPC) and software deﬁned networking (SDN) [
 19
 ]. The main advantages of containers
over virtual machines (VMs) lie in two areas. Firstly, containers can share resources and
utilize the same operating system (OS) kernel, whereas VMs require their own individual
copies [
 20
 ]. Secondly, containers can be initiated and terminated almost instantaneously,
whereas VMs require a signiﬁcant amount of time to start [
 21
 ]. In addition, containers have
proven to be more eﬀective than VMs in certain scenarios, such as microservices, because
they are lightweight and do not necessitate a complete OS copy for each image.
These
beneﬁts come at the cost of abstraction since almost all container components are virtu-
alized. This results in monitoring and securing containerized applications that are harder
than monolithic applications because containers are short-lived processes making it diﬃcult
to associate causes of errors with the container causing them. Also, by default, all containers
in Docker run as root user. If the container process gets compromised, it can be used to gain
lateral access and cause severe damage. Docker [
 22
 ] is the most commonly used container-
ization framework to run containers. It combines Linux cgroups, namespaces, volumes, and
systemd slices to isolate and concurrently run containers on a given host. Kubernetes uses it
to run containers on nodes in an isolated manner so they cannot interfere with one another.
2.1.2
Container Orchestration Systems
A key technology used for managing containers is Kubernetes (K8s) [
 23
 ]. Kubernetes
divides our distributed cluster into 2 types of nodes, namely master nodes and worker nodes.
The worker nodes are responsible for executing pods, while the master node orchestrates
and schedules pods. Pods consist of a collection of co-located Docker containers tasked with
performing a singular functionality. The master node runs a REST API that can dynamically
adjust to manage and organize worker nodes as deployments and services. The kubectl
API is a powerful tool that provides us with an interface to our cluster and conﬁgures it to
provide optimal security. We can use kubectl to describe our cluster components and view
debugging information, but this task is manual-intensive. Also, Kubernetes suﬀers from the
23



--- PAGE 24 ---
phenomena of hysteresis, i.e., the conﬁguration we want our cluster to be in may not exactly
be the current state, and there is the possibility of conﬁguration drift. The full capabilities
and features of kubectl are beyond the scope of this thesis, but more information can be
found in the documentation [
 12
 ].
Kubernetes [  12
 ] is a highly modular and extensible open-source container orchestration
platform that automates containerized applications’ deployment, scaling, and management.
Initially developed by Google and now maintained by the Cloud Native Computing Foun-
dation (CNCF), its architecture consists of interconnected components that work together
to manage the lifecycle of containers and the resources they consume. Kubernetes has been
architected to handle the complexity of distributed systems and the challenges of scaling and
managing large containers.
Kubernetes architecture is divided into two components: the control plane and the worker
plane.
Control plane nodes act as the orchestrator for our worker nodes by scheduling,
providing conﬁguration, and monitoring the system’s status. On the other hand, the worker
nodes provide the container runtime responsible for running and managing the container’s
lifecycle. Unless speciﬁed otherwise, all application pods run inside our worker nodes as
containers. The control plane node monitors the resource availability in our worker nodes
and schedules pods for them. Kubernetes also provides Kubernetes Metrics Server, a metrics
collection pipeline that can analyze metrics for autoscaling. Using Kubernetes Metrics Server
for observability or any use case other than autoscaling is not advised.
2.1.3
Microservices
The microservices approach to software development, sometimes called a microservices
architecture, divides functionality into multiple independent applications. Each independent
application is much smaller than a monolithic program and only handles one function. To
perform a task, the independent applications communicate over a network [
 24
 ]. Microser-
vices have emerged as a popular pattern for developing large-scale applications in cloud en-
vironments for their ﬂexibility, scalability, and agility beneﬁts. The cloud-native landscape
comprises thousands of single-concern, loosely-coupled microservices running on container-
24



--- PAGE 25 ---
ized platforms like Docker. This approach can oﬀer several beneﬁts, including improved
scalability, ﬂexibility, and resilience. However, it also introduces new challenges, such as the
need for eﬀective service discovery and monitoring and the potential for increased complexity
in testing and deployment [ 25
 ].
One of the key challenges of microservices is ensuring observability, or the ability to
monitor, debug, and diagnose issues within the system [
 26
 ]. This is especially important in
distributed systems, where failures or issues can occur in various parts of the system, and it
can be diﬃcult to trace their root cause. Because microservices are typically distributed and
highly decoupled, traditional monitoring approaches may not provide full visibility into the
system’s behavior [ 27
 ]. Several approaches and tools have been developed for observability
in microservices to address this challenge.
One approach is to use distributed tracing, which involves capturing and correlating trace
data from individual service instances as they handle requests [
 28
 ]. Distributed tracing can
provide end-to-end visibility into requests across multiple services, allowing developers to
quickly identify bottlenecks and diagnose issues. Tools like Zipkin [
 29
 ] and Jaeger [
 30
 ] have
been developed to support distributed tracing in microservices.
Another approach is to use log aggregation and analysis, which involves collecting log
data from multiple services and correlating it to gain insights into system behavior. Log
aggregation can help identify patterns and anomalies in system behavior and provide a
centralized source of truth for debugging and troubleshooting [
 31
 ].
Finally, some approaches combine tracing and logging with metrics and other telemetry
data to provide a more comprehensive view of system behavior. Metrics can provide insights
into resource utilization, while telemetry data can help identify system-level issues like net-
work latency and service availability [
 27
 ]. Tools like Prometheus [ 32
 ], and Grafana [
 33
 ] have
been developed to support this approach to observability in microservices.
Observability is a key challenge for microservices, but several approaches and tools have
been developed to address it. Distributed tracing, log aggregation and analysis, and teleme-
try data are essential to providing insights into system behavior and help developers quickly
identify and diagnose issues.

2.2
Network Service Mesh
Service mesh is an implementation improvement over microservices that helps to simplify
the management of networking between microservices by providing a standardized approach
that can be applied across multiple applications and environments.
Additionally, a ser-
vice mesh can help to address some of the challenges of microservices, such as observability
and security [ 34
 ]. A service mesh is an infrastructure layer designed speciﬁcally to man-
age communication between services in a system. Its primary responsibility is to ensure
that requests are delivered reliably through the intricate network of services that make up
a modern cloud-native application. The service mesh is typically implemented using a set
of lightweight network proxies that are deployed alongside the application code, without re-
quiring the application to have any knowledge of them [
 35
 ]. As shown in Figure
 2.1
 , a service
mesh infrastructure logically consists of a data plane and a control plane. The data plane
consists of a collection of intelligent proxies that are commonly deployed as sidecars [
 36
 ].
These proxies regulate and oversee all network communication between microservices. With
full visibility into each network packet, the data plane is responsible for service discovery,
health checking, routing, load balancing, authentication/authorization, and observability.
On the other hand, the control plane oversees and conﬁgures the proxies to manage traﬃc
routing. Moreover, the control plane conﬁgures corresponding components to enforce poli-
cies and collect telemetry. In essence, the control plane serves as the central control hub or
brain of a service mesh.

 ]

2.2.1
Data Plane
In a microservice architecture, the data plane typically involves deploying sidecars along-
side each service instance that requires communication with other services in the system.
These proxies act as intermediaries for all requests and responses related to the service, and
can handle a variety of tasks such as authentication,authorization, encryption, rate limiting,
service discovery, logging, tracing, and load balancing [
 38
 ], [ 39
 ]. By implementing a service
mesh, the network communication logic is separated from the application logic, eﬀectively
eliminating the need for developers to concern themselves with the intricacies of network
communication. Instead, the service can interact solely with its local proxy. Additionally,
a service mesh enables consistent implementation of network communication and related
features across services, even when they are developed in diﬀerent programming languages
by diﬀerent teams, without requiring duplication of eﬀort. Sidecars are ideal standardized
locations to collect observability data about the networking in our applications. It is impor-
tant to note that the sidecars are present on the same machine as the service it is proxying,
and they communicate over the loopback interface “localhost”. This does add some minor
latency to our application, and we wish to avoid this if possible.
2.2.2
Control Plane
In microservice-oriented systems, which may consist of numerous services that are repli-
cated multiple times for the sake of performance and reliability, a corresponding number of
proxies must be managed. This number can easily reach dozens or even hundreds in larger
systems. The control plane helps an administrator conﬁgure the behavior of all our proxies
from a central API. The administrator can update conﬁgurations using YAML or REST calls
to specify the routing, service discovery, health checking, load balancing, and observability
needed in our service mesh architecture. Each data plane proxy must connect to the control
plane to register itself and receive conﬁguration details. The control plane is usually an
independent node in our microservice mesh cluster with its own dedicated hardware. All
the proxies pull the latest conﬁgurations from the control plane server and push the latest
27



--- PAGE 28 ---
observability data to the control plane. The control plane knows all the performance errors
or latency of the distributed proxies report.
2.2.3
Ingress
The ﬁnal component in a service mesh is the ingress gateway, which acts as a public
entry point to the services in our mesh. The ingress gateway is an independent entity that
implements Layer 7 and Layer 4 routing, sometimes called HTTP or path-based routing.
This gateway determines which traﬃc enters the service mesh and what packets leave the
service mesh, also known as North-South traﬃc. The ingress gateway plays a crucial role in
distributed tracing in OpenTelemetry. We can associate unique trace IDs whenever a user
tries to establish a new connection with the ingress gateway. This trace ID can then be
propagated and recorded throughout the data plane to achieve complete observability in a
service mesh. We leverage the Envoy Proxy [ 40
 ] as the ingress load balancer for our solution,
but other alternatives like Istio and Linkerd are also possible solutions.
2.3
Observability
Distributed architectures, by their very nature, are considerably more intricate, and
present a multitude of operational diﬃculties concerning performance and availability. To
address these challenges, we require observability data that can assist us in gaining a better
understanding of these environments. Observability comes from control theory and measures
how well a system’s internal states can be inferred based on external outputs. The more
questions we can ask and answer about the system, the more observable it is. In the context
of microservice, observability comprises three main data types: metrics, logs, and traces.
Metrics are the variables that can be measured by looking at the system from the outside.
Metrics are a numeric representation of data measured over intervals of time. Metrics can
utilize mathematical modeling and prediction to derive knowledge of a system’s behavior
over time intervals [
 26
 ]. Since numbers are optimized for storage, processing, compression,
and retrieval, metrics enable longer retention of data as well as easier querying. Logs are
an immutable, timestamped record of discrete events that happened over time.
Finally,
28



--- PAGE 29 ---
traces represent the interaction amongst multiple distributed applications and the ability
to obtain a macro view of the request-response lifecycle.
A single request may involve
multiple services or components spread across diﬀerent servers or geographical locations in
a distributed system. Each of these services may generate its metrics, logs, and traces, but
with a way to link them together, it can be easier to understand the end-to-end behavior of
the system. A trace solves this problem by injecting a unique identiﬁer (called a trace ID)
for each request and propagating it across all the components involved in the request. As
the request ﬂows through the system, each service adds timing and other metadata to the
trace, creating a detailed view of the entire transaction. This section deﬁnes the observability
solutions in Kubernetes and their technical details.
2.3.1
Instrumentation for Observability
Traditional observability for monolithic applications depends solely on the programmer’s
capabilities to add additional code and import libraries that export observability data to be
consumed. This approach requires the expensive operational overhead of programming and
redeploying any additional observability functionality we wish to add. Another drawback of
instrumenting our applications with observability code is the vendor lock-in and lack of inter-
compatibility between various libraries. Grafana’s 2023 observability survey [
 41
 ] highlighted
that most organizations utilize 10-70 diﬀerent libraries in their technology stack to monitor
the various microservices in their organization. There is a growing need for a standardized
data model that is vendor-agnostic and compatible with any technology stack.
2.3.2

create and manage telemetry data such as traces, metrics, and logs. OTel is an open-source

formed as a result of the merger of OpenTracing and OpenCensus projects.
It aims to
deﬁne and standardize how telemetry data is received, processed, and stored from diﬀerent
sources. OTel provides libraries and SDKs which can be imported into your application; it

the Open Telementry Protocol (OTLP) to share telemetry data. Some popular options for

Opentelemetry agent standard deﬁnes the data model, protocol (OLTP), and payload

2.3.3
Prometheus
Prometheus [  32
 ] is a time series database created by SoundCloud in 2012 and was the
second project to be incubated by CNCF after Kubernetes. Time series means that changes
are recorded over time. Prometheus collects telemetry data from conﬁgured targets at given

intervals, evaluates rule expressions, displays the results, and can trigger alerts when speciﬁed
conditions are observed.
One of the key features of Prometheus is its query language, PromQL, which allows users
to retrieve and manipulate time series data collected by the Prometheus server. PromQL
supports a wide range of operations, such as ﬁltering, aggregation, and arithmetic trans-
formations, and can be used to generate complex queries that provide insights into system
performance and behavior.
Its data model is at the core of Prometheus, which deﬁnes how metrics are collected,
stored, and queried. Prometheus uses a time-series data model, where each metric is repre-
sented as a series of timestamp-value pairs that can be queried and visualized over time. The
data model also includes concepts such as labels and metrics types, which help to organize
and categorize metrics.
Prometheus collector gets information by using per-node exporters deployed as Kuber-

systems. In addition, exporters are helpful for cases where it is not feasible to instrument
a given system with Prometheus metrics.

2.3.4
Extended Berkeley Packet Filter (eBPF)
eBPF has gained attention from many tech giants to improve their system performance
and observability. Facebook’s Katran [
 48
 ] uses eBPF for Layer-4 load balancing, TCP tuning,
and DDoS protection. Google’s Adeb [
 49
 ] provides an Android operating system with a
Linux shell environment with tracing and high-security features. Netﬂix uses eBPF heavily
in its networking stack for adding observability to the packets coming into its services.
Cloud providers like AWS, Microsoft, and Google use eBPF for security [
 50
 ], [  51
 ], network
optimization [
 52
 ], virtualization [
 53
 ], and monitoring [
 54
 ].
Linux Berkeley Packet Filters (BPF) have evolved over the past few years, making them
the ideal tool for kernel tracing and metric collection. The original BPF patch [
 55
 ] was
added in 1992 for a speciﬁc purpose: to provide applications that monitor the systems
network with direct information from the kernel.
The tcpdump command in Linux was
the ﬁrst to use the packet ﬁlter. BPF introduced two signiﬁcant innovations; ﬁrst, a new
VM was created inside Linux designed to work eﬃciently with the CPU register. Second
was the introduction of a per-process buﬀer, which removed the need to copy data into the
kernel before processing. The Extended Berkeley Packet Filter (eBPF) was added to Linux
version 3.14 by Alex Starovoitov, improving the instruction set for the VM and increasing
size to 64 bits and the number of registers to 10.
The increase of the number and size
of registers created new opportunities for programmers to develop more intricate software,
as they could now transfer a greater amount of information through function parameters.
One of the most popular service mesh projects to rise from eBPF is Cilium [ 56
 ]. Cilium is

2.3.4.1
Architecture
BPF is a sophisticated virtual machine that executes code instructions in an isolated
environment. BPF is compatible with compilers such as LLVM and GNU Compiler Collec-
tion (GCC), which enable the translation of C code into BPF instructions. Although these
37



--- PAGE 38 ---
instructions are similar to JVM bytecode in the Java programming language, they are Just-
In-Time (JIT) compiled by the Linux kernel when called. The JIT will transform the BPF
bytecode into machine code directly after verifying the program, avoiding this overhead on
execution time. One powerful beneﬁt of eBPF is that we do not need to restart our system
to load BPF programs, then can be loaded on-demand dynamically.
Executing arbitrary code in the kernel can result in diﬃcult bugs which cause the system
to crash. To avoid this, the BPF veriﬁer must verify the BPF bytecode. The conditions it
checks for are:
• No inﬁnite for loops should be present in the program.
• The size of the program should not exceed 4096 bytes.
• Program doesn’t attempt unauthorized memory access outside the buﬀer provided.
Finally, the kernel must know when and where to run any BPF program, known as
the probe or execution point where the program is attached. There are over 2000 probe
locations in the kernel, and the list is growing [
 57
 ]. The execution point can be a kernel
function (kprobe), a function in your application (uprobe) or any arbitrary tracepoint in the
Linux codebase.

Berkeley Packet Filter (BPF) programs are tiny programs that can be executed within
the kernel to perform various network-related tasks; BPF programs can be written in C or
assembly language and compiled into a bytecode format that the kernel can execute. BPF
programs take the binary of the OS they are instrumenting as a dependency input to their
program; this is required since the BPF compiler must understand how the memory layout
is organized and what region of memory can be accessed. Figure

protocol type. The program takes a pointer to a struct __sk_buff structure as input,
which contains information about the network packet being processed.
The program ﬁrst extracts the Ethernet header and IP header from the network packet
and checks to ensure they are within the bounds of the packet data. If either header is absent,
the program returns a value of 0 to indicate that the packet should be dropped. Next, the
program checks the source IP address of the packet to see if it matches a speciﬁc value
(0x02020304 in this example). If the address does not match, the program returns a value
of 0 to indicate that the packet should be dropped. Finally, the program checks the packet’s
protocol type to see if it is TCP. If the protocol is not TCP, the program returns a value
of 0 to indicate that the packet should be dropped. If the packet passes all of these checks,
the program can perform some action on the packet data (for example, it could update a
packet counter or send the packet to another kernel module for further processing). In this
example, the program returns a value of 1 to indicate that the packet should be accepted.

2.3.4.4
libbpf
libbpf is a low-level library for working with eBPF programs and maps, providing a C
API for loading, verifying, and manipulating eBPF objects. It is designed to be lightweight,
portable, and easy to use in user-space programs. libbpf provides functions for loading
eBPF bytecode from a ﬁle, verifying it, and loading it into the kernel. It can also load and
verify eBPF maps, and data structures allowing eBPF programs to store and share data
with user space. One of the critical features of libbpf is that it enables eBPF programs and
maps to be compiled once and run anywhere, as long as the target system supports eBPF.
When we compile an eBPF program with libbpf, it generates a binary object ﬁle containing
the eBPF bytecode and map data and metadata about the eBPF objects. This binary object
ﬁle can be loaded into the kernel on any system that supports eBPF. The eBPF program
or map will execute as expected, regardless of the kernel version or system conﬁguration.
This CO:RE “compile once, run anywhere” approach makes it easy to develop and deploy
eBPF programs and maps across multiple systems without worrying about kernel or system
compatibility issues. libbpf is often a building block for higher-level eBPF tools like BCC.
2.3.4.5
BCC
BCC is another high-level toolkit that provides out-of-box eBPF program management
and deployment. BCC uses Python to load, verify and manipulate eBPF objects. BCC
comes with the LLVM compiler to convert Python code to BPF programs; therefore, there is
more convenience at the cost of additional overheads. BCC provides multiple command-line
tools for tracing and proﬁling Linux systems, such as trace, profile, offcputime, and
opensnoop. These tools use eBPF to trace system calls, kernel functions, and other events
and can provide detailed information about system performance and resource usage. BCC
also oﬀers multiple helper functions to write your own BPF programs, such as the bpf_text
utility for writing eBPF programs in a higher-level language and the bcc_perf library for
working with eBPF maps. Due to the additional overhead of compiling Python code to the
target Operating System, BCC is not recommended for heterogeneous multi-node cluster
environments.

2.4
Chaos Engineering
Chaos engineering is the process of intentionally introducing faults into a system to
identify weaknesses, test failure scenarios, and enhance the system’s overall resilience. The
objective is to conduct controlled experiments in a production environment to determine
how a system responds to various failure scenarios, such as network outages, service failures,
high-stress load or hardware crashes [
 59
 ].
44



--- PAGE 45 ---
The main aim of chaos engineering is to improve conﬁdence in a system’s ability to handle
unexpected events and reduce the probability of downtime or other critical incidents. By
proactively testing a system’s ability to handle failures, businesses can recognize potential
vulnerabilities and improve their systems before real-world failures occur.
To implement chaos engineering, we must ﬁrst identify its systems’ critical components
and failure modes.
Then we can then design experiments that simulate various failure
scenarios and evaluate the system’s response to those failures. This could involve deliberately
disrupting service traﬃc, terminating processes, or introducing latency or errors into the
system.
Eﬀective chaos engineering aims to ensure that experiments are well-designed, well-
controlled, and do not have unintended consequences that aﬀect the system’s stability. It is
also crucial to have a clear understanding of the system’s architecture and dependencies, as
well as monitoring and alerting systems to quickly detect and resolve any issues that may
occur during chaos experiments.
In summary, chaos engineering is a potent tool for enhancing the resilience of complex
systems and minimizing the risk of downtime or other critical incidents. However, it requires
careful planning and execution to ensure that experiments are safe and eﬀective and that
the system remains stable throughout the process.

Node Observability Agents
Finally, we must deploy an agent for every node in our cluster to achieve host-level
observability. AWS uses this approach in their CloudWatch agent and by GCP in their
Stackdriver agent. Most host-level observability agents are root-level applications that can
access the /proc virtual ﬁle system. The /proc folder doesn’t contain real ﬁles but runtime
system information [

 ] (e.g., system memory, devices mounted, hardware conﬁguration,
etc.).
For this reason, it is regarded as a control and information center for the kernel.
Prometheus’s NodeExporter is a wrapper that reads data from the proc folder and serves
it at an HTTP endpoint. cAdvisor is a tool from Google that exports Prometheus metrics
like NodeExporter but provides the breakdown of resource utilization per container, i.e., it is
a container-aware exporter. Exporters like NodeExporter and cAdvisor provide time series
metrics by sampling the data in the /proc folder. Sample means that once every speciﬁed
time interval (minimum 1 second), Sampling can cause us to lose information [
 71
 ]. Still, it
is necessary to reduce the amount of storage and network usage for monitoring.
Using cAdvisor and Node Exporter, we can obtain baseline telemetry information about
CPU Utilization and RAM Utilization at the node level (Node Exporter) and the pod
level(cAdvisor). This information is useful for getting up and running with metrics, but
both of these tools do not allow custom metrics to be exported outside their scope. Also,
since they are sampling the information, it is possible to lose the granularity of the data. A
high resource consumption but short lifespan process might be running in our cluster, but
these tools would not pick up such a process. Therefore, we need custom metric information
from our nodes that can run without adding much overhead and not use sampling to get
complete information.
To create custom metrics at the host level, we leveraged the eBPF exporter from Cloud-
ﬂare. The eBPF exporter works by running eBPF programs within the kernel of a Linux
system and collecting metrics directly from the kernel. These metrics may include system
performance, resource utilization, network traﬃc, and more information. The metrics are
written to an eBPF Map, and all the events are captured without dropping any information.
eBPF exporter will then poll the eBPF maps to fetch kernel-level traces from the host. Us-

network, and host layer metrics and traces. The collector is deployed once per cluster, com-

4.3.5
Network Performance
The locust load generator described in Sec
 4.3.2
 directs requests to the Envoy frontend
proxy exposed on port 8080. Envoy is responsible for adding distributed trace ID information
to all requests, allowing us to track them in our network.
OpenTelemetry collector can
combine all the traces generated by microservices and the diﬀerent endpoints accessed by
the locust script. Once exported to Prometheus we can use Grafana for visualization of
distributed traces, as shown in Figure
 4.17
 .
Figure 4.17. OpenTelemetry distributed trace visualized on Grafana dashboard
While distributed tracing is a powerful tool for monitoring and analyzing application
performance, it is not enough for network observability.
Network observability requires
more comprehensive visibility into the network, including the performance and behavior of
the network itself and the applications and services that rely on it. Some limitations of
OpenTelemetry and Envoy-based network observability that we identiﬁed are:
1. Limited visibility into the network: Distributed tracing is only concerned with
tracing the path of a request through the application stack, which may not provide
enough visibility into the network itself. It is not be able to identify issues that are
speciﬁc to the network, such as congestion or routing problems.
2. Inability to capture low-level metrics: Distributed tracing is able to capture high-
level information about requests, such as their latency or the services they interact
80



--- PAGE 81 ---
with. It does not capture lower-level details about network behavior, such as packet
loss, latency variation, or network topology changes.
3. Sampling: Distributed tracing can generate a large volume of data that needs to be
stored and processed, it is necessary to use sampling techniques which results in loss
of holistic information.
4. Operational overhead: Distributed tracing requires instrumentation of all compo-
nents in the application stack to generate trace data. We had the beneﬁt of leverag-
ing OpenTelemetry’s demo which came pre-instrumented but it required considerable
eﬀorts from the open-source community to get distributed traces and not all microser-
vices in the demo support them yet.

5. CONCLUSIONS AND FUTURE WORK
5.1
Conclusions
To solve the problem of microservice observability, this thesis aims at developing open-
source toolkit that can collect and analyze application-layer, network-layer, and host-layer
metrics for any Kubernetes deployment. We investigated the observability performance of
NodeExporter, cAdvisor, eBPF exporter, Envoy and OpenTelemetry in a Kubernetes cluster.
We also used the Chaos Mesh library to inject anomalies and detect them. The goal was to
evaluate the eﬀectiveness of each observability tool in detecting and mitigating anomalies in
a distributed system.
Our experiments showed that OpenTelemetry and Envoy distributed traces were the
most eﬀective tools in detecting anomalies and providing a comprehensive view of the sys-
tem. OpenTelemetry provided a holistic approach to observability by collecting metrics,
traces, and logs, while Envoy distributed traces allowed for detailed tracing of service-to-
service communication. However, OpenTelemetry and Envoy required the most rewriting of
the application codebase to achieve this detailed observability. Another drawback of Open-
Telemetry was the requirement of deploying an Opentelemetry Collector sidecar to ingest
OLTP data. This added task of exporting OpenTelemetry metrics and traces to Prometheus.
OpenTelemetry has attempted to enable push-mode data exporting directly to Prometheus
but it is in not yet supported. This further increased the operational overhead of enable
NodeExporter and cAdvisor provided system-level metrics but were limited in providing
application-level telemetry data. We also found that the eBPF exporter was a powerful tool
for monitoring various metrics, including network traﬃc, system calls, and kernel events.
eBPF exporter was highly ﬂexible and could be integrated with other observability tools like
Prometheus and Grafana.
While eBPF exporter has a steep learning curve and requires specialized knowledge of
low-level system programming, it provides a more granular view of the system’s perfor-
mance than NodeExporter and cAdvisor. eBPF exporter can collect a wide range of teleme-
try data, making it useful for monitoring the performance of complex distributed systems.
eBPF scripts do require programming eﬀort similar to OpenTelemetry. Still, rather than
84



--- PAGE 85 ---
instrumenting each application independently, eBPF only requires one-time eﬀorts by the
developer to get observability for the entire distributed cluster.
Network-level observability was the most challenging to achieve Our research highlights
the importance of choosing the right observability tools for monitoring distributed systems
in Kubernetes clusters. Depending on the needs of your application, you may choose one
or more of these tools to provide observability and monitoring. OpenTelemetry and Envoy
distributed traces provide a more comprehensive approach to monitoring the performance
of complex distributed systems however, it requires extensive programming eﬀort. NodeEx-
porter and cAdvisor helped get system-level metrics without any programming required, but
we could not extend their functionality to generate custom metrics. eBPF exporter provides
a more detailed and ﬂexible approach to monitoring system performance. The Chaos Mesh
library was a valuable tool for evaluating the resilience of observability tools in detecting
and mitigating anomalies in distributed systems.
5.2
Future Research Directions
This thesis tackles the problem of microservice observability in cloud-native environments
in order to keep up with the fast-growing demand for cloud-based application deployments.
There are still many exciting use cases of eBPF-based observability for further exploration.
Here, we introduce three for potential future research directions: sidecarless service mesh,
multi-cloud observability, and automated anomaly detection ML models.
Sidecarless service mesh. Service meshes have become the norm for managing net-
working between microservices-based applications in the cloud. None of the tools in our
study were able to provide complete network-layer observability for Kubernetes-based work-
loads. Cilium, an open-source CNI for Kubernetes uses an eBPF-based data plane, which
provides deep visibility into network traﬃc at the kernel level. eBPF functions allows for the
creation of highly eﬃcient and customized network probes that can capture detailed network
traﬃc data in real-time. Cilium uses eBPF probes to collect detailed network layer metrics,
including packet loss, latency, and throughput. Cilium also includes a distributed tracing fea-
85



--- PAGE 86 ---
ture that allows for the correlation of network-level observability data with application-level
observability data, enabling end-to-end observability across the entire stack.
Multi-cloud observability. This thesis focuses on deploying our cloud observability
solution on the chameleon cloud provider. Multi-cloud deployments are becoming increas-
ingly popular for higher availability and vendor lock-in reduction. We did not explore the
possibility of a truly homogeneous cluster conﬁguration comprising nodes hosted on diﬀerent
clouds. Multi-cloud environments can be complex and diverse, with a variety of diﬀerent
operating systems, platforms, and cloud providers. eBPF provides a standardized way to in-
strument the Linux kernel across diﬀerent environments, allowing for consistent monitoring
and observability across multiple clouds.
Automated anomaly detection. AIOps, or Artiﬁcial Intelligence for IT Operations,
is a methodology that uses AI and machine learning to improve the eﬃciency, speed, and
accuracy of IT operations. This thesis provides a complete toolkit and data collection pipeline
for observability data collection of the application-layer, network-layer and kernel-layer. The
Prometheus data can be used for anomaly detection with machine learning by feeding the
time-series data into machine learning models that can detect unusual patterns or trends
that may indicate an issue with the IT infrastructure. Some algorithms that may be used
for this work are isolation forests, autoencoder neural networks and one-class support vector
machine. In order to use Prometheus data for anomaly detection with machine learning, the
data needs to be preprocessed and transformed into a format that can be used by the machine
learning algorithms. This may involve feature engineering to extract relevant features from
the time-series data, normalization to ensure that the data is on a consistent scale, and
splitting the data into training and testing sets for the machine learning models.
